Introduction

This document describes the architecture and detailed design of the Dynamic Resilient Grid (DRG) framework: a demand-side analytics system that forecasts neighbourhood-level electricity demand, detects statistically defined stress periods, and quantifies how electric-vehicle and heat-pump adoption amplifies peak demand on UK urban distribution networks.

Purpose

The purpose of this document is to define an implementable, reviewable architecture that satisfies the business requirements set out in DRG-BRD-001. It records the structure of the system, the responsibilities of each component, the interactions between them, the design decisions taken and the reasoning behind those decisions, so that the system can be built, assured, operated and extended by parties other than its original author.

Project Overview

Problem statement

Urban low-voltage distribution networks in the United Kingdom were dimensioned for a domestic load profile that is now changing faster than the assets serving it. Two electrification vectors dominate that change. Uncontrolled domestic electric-vehicle charging concentrates a 7 kW load into the evening window that already contains the daily demand peak. Electrified heating replaces a gas load with an electrical one that rises precisely when the weather is coldest and occupancy highest.

Both loads are individually well understood. What network planners lack is a way to quantify, at the granularity of an actual neighbourhood and an actual half-hour, how far a given adoption trajectory pushes local demand beyond its historical envelope - and to do so from the data they already hold, namely smart-meter consumption records, without waiting for network telemetry that may never be instrumented at that level.

Conventional practice relies on historical averages and diversified design figures. These are sound for steady-state planning but silent on three questions that matter for electrification: how often demand will exceed its historical envelope, for how long each such episode will last, and which conditions drive those episodes.

Aim

Aim To design, implement and evaluate an AI-driven forecasting and electrification stress-modelling framework that quantifies neighbourhood-level demand risk under future electric-vehicle and heat-pump adoption scenarios, using demand-side smart-meter data and publicly available contextual data only.

Research questions

  1. RQ1 - How accurately can machine-learning models forecast half-hourly local electricity demand using smart-meter data?
  2. RQ2 - How sensitive is neighbourhood peak demand to varying EV and heat-pump adoption levels?
  3. RQ3 - To what extent does electrification amplify stress frequency and peak intensity?
  4. RQ4 - Which temporal and statistical features contribute most to high-demand stress prediction?

Each question maps onto a measurable output of the system: RQ1 to the evaluation metrics of the model ladder; RQ2 and RQ3 to the adoption sensitivity grid; RQ4 to the stress-conditional SHAP attribution. The architecture is arranged so that answering them is a by-product of running the pipeline, not a separate manual analysis.

What the system is not

Boundary of validity DRG performs no physical power-flow modelling. It has no network topology, no transformer or cable ratings, and no voltage or thermal model. "Stress" is a statistical statement about a demand distribution, not an engineering statement about an asset. The output identifies where and when to look and how much worse electrification makes it; it does not by itself justify a reinforcement decision, which requires asset data the source dataset does not contain.

Architecture Overview

Architectural drivers

Four forces shaped the architecture more than any others.

  1. The data cannot leave its custody, and may not be redistributed. This drives a design in which the repository is fully runnable without the licensed data, and ingestion is a pluggable stage rather than a precondition for every other stage.
  2. Memory is bounded before the dataset is. Ingestion must aggregate inside the read loop, not after it.
  3. An analytical claim is only as good as its reproducibility. Every stochastic element is seeded, every stage caches a typed artifact, and every run emits a machine-readable report that regenerates the published figures.
  4. Scenario results are policy-adjacent. Parameters that materially change the headline number must be explicit, defensible against published planning figures, and auditable in the output rather than buried in code.

Layered view

Design principles

Principles applied throughout the design
PrincipleApplication in DRG
Stages are pure functions over tablesEach stage reads a typed table, returns a typed table and caches it. Any stage can be re-run alone; the cloud training job and the local CLI call the identical functions, so there is no second code path to keep in step.
One feature builderTraining, replay and the API all call drg.features.engineering. Train/serve skew becomes structurally impossible rather than a discipline to maintain.
Never claim data you do not haveEvery derived series carries a source column and degrades in documented steps: measured, then proxy, then synthetic.
Fix the yardstick before the experimentStress thresholds are estimated on the historical baseline and then held constant, so a scenario that raises demand raises measured stress instead of moving the threshold with it.
Assert physical sanityThe simulation reports ADMD per technology and energy per vehicle per day; automated tests assert equipment ratings are never exceeded and that daily EV energy stays within the range implied by UK average mileage.
Fail loudly, degrade quietlyA missing model is a 503 naming the command that fixes it; an unavailable API is a logged fallback that does not stop the pipeline.

Key architectural decisions

Decision record
RefDecisionRationale and rejected alternative
AD-01Statistical stress definition (P95 of own history)No asset ratings exist in the dataset. Rejected: assuming a nominal transformer rating, which would have produced authoritative-looking numbers resting on an invented constant.
AD-02Gradient boosting as the primary modelThe target responds to sharp threshold-like interactions (evening peak x cold x weekday) that trees capture directly, and TreeSHAP gives exact attribution cheaply. Rejected: deep sequence model as primary - marginally worse here and far harder to explain and serve.
AD-03Bottom-up, household-level electrification simulationProduces a genuine diversity effect and exposes auditable per-household quantities (ADMD). Rejected: a flat multiplier on the aggregate profile, which cannot represent coincidence.
AD-04Calibrated synthetic fallback datasetMakes the entire framework runnable, testable and shareable without the licensed extract. Rejected: committing a data sample, which the licence forbids.
AD-05Azure Container Apps over AKSThree small services and a nightly batch job; scale-to-zero and a native cron job type cover the workload without a cluster to operate. Rejected: AKS, disproportionate to the load.
AD-06Shared Azure Files volume between batch and servingThe batch job writes data and models that the API and dashboard read immediately; removes a separate synchronisation step. Rejected: blob-download-on-start, which adds cold-start latency and a failure mode.
AD-07Separate application and model release pipelinesCode and models have different risk profiles, cadences and approvers. A model change must pass a quality gate; a documentation change must not.
AD-08Tabular model always served, even if a sequence model scores betterThe serving contract is a design matrix; sequence models need a frame. The trainer records the fact in its log rather than silently serving something the API cannot call.

Component diagram

Why the dependency direction matters ElectrificationSimulator depends on nothing but numeric libraries, and StressDetector depends on nothing at all beyond the demand table. That is deliberate: these two components carry the analytical claims of the project, so they are kept free of configuration, I/O and framework coupling and can be exercised exhaustively in unit tests. The orchestrator, not the domain components, owns all knowledge of where data lives.

Domain class model

Configuration objects as first-class domain types EVConfig and HeatPumpConfig are not bags of settings; they are the scientific parameters on which every headline number depends. Modelling them as typed classes with documented defaults, a from_config() factory and unit tests asserting their physical consequences is what turns "we assumed 7 kW charging" from a code comment into a reviewable artefact.

Data Architecture

Data flow and lineage

Data moves through five persisted stages. Each is a typed columnar table, cached so that any stage can be re-run without repeating its predecessors, and each carries provenance forward.

Persisted data products
ArtifactFormatContent and grain
neighbourhood_demandParquetOne row per (timestamp, neighbourhood). Cleaned half-hourly demand, household count, temperature, provenance.

Ingestion design

The published Low Carbon London half-hourly release is several gigabytes of CSV with the columns LCLid, stdorToU, DateTime, KWH/hh (per half hour). Three design responses follow from constraint CN-02.

  • Aggregate inside the read loop. Each chunk is grouped to (timestamp, neighbourhood) before the next chunk is read, so peak memory is proportional to chunk_size, not to the file.
  • Stable grouping. Households map to neighbourhoods by a BLAKE2b hash of the meter identifier modulo the group count. Unlike Python's built-in hash(), which is salted per process, this is reproducible across runs and machines.
  • Tolerant column resolution. The publisher's column spellings vary between releases, so columns are matched case- and whitespace-insensitively with documented fallbacks.

Data quality treatment

Cleaning rules and their justification
RuleParameterJustification
Grid regularisation30-minute indexReindexing to a complete grid makes missingness explicit rather than implicit.
Robust outlier clipping6 x MADMedian absolute deviation is not itself distorted by the spikes it is meant to detect, unlike a standard-deviation rule.
Short-gap interpolation≤ 6 periods, interior onlyMeter communication losses of up to three hours are recoverable; longer gaps are not invented.
Day coverage filter≥ 80% of 48 periodsA day with heavy missingness would understate its own peak and corrupt the percentile threshold.
Provenance is a first-class column, not documentation The carbon-intensity API archive begins in 2018, while the study period is 2011-2014. Rather than silently substituting or silently omitting, the client projects a month-by-half-hour climatology from a recent reference year and tags every row climatology-proxy. A reader of the data can therefore tell measurement from projection without consulting this document. The same discipline applies to temperature and to the demand table itself.

Machine Learning Architecture

Feature design

Feature groups
GroupFeaturesRationale
Calendarhour, half-hour period (0-47), day of week, month, season, week of year, weekend flag, UK bank-holiday flag, evening-peak flagDomestic demand is driven by routine before it is driven by weather.
Cyclicalsin/cos of period, day of week and day of yearGives linear models the same access to periodicity that trees obtain by splitting.
Lagst-1, t-2, t-3, t-48 (yesterday), t-96, t-336 (last week)Autoregressive structure; the weekly lag proves to be the dominant driver.
Rolling statisticsmean, standard deviation, min, max over 3 h, 1 day and 1 weekLocal level and volatility, all computed on shifted values.
Dynamicsramp rate, ramp acceleration, daily and weekly deltas, load factorThe rate of change discriminates the rising edge of the evening peak.
Exogenoustemperature, heating and cooling degrees, lagged and smoothed temperature, HDD x evening interaction, carbon intensityWeather sensitivity is the channel through which heat-pump electrification will act.
Two invariants, both enforced by automated tests Rolling statistics are computed from shift(1) values, so the current observation can never enter its own prediction; and every lag is computed within a neighbourhood group, so no information crosses site boundaries. These are the two ways a load-forecasting result is most commonly and most quietly invalidated.

Validation protocol

Splitting is chronological throughout: a training window, then a validation window used for early stopping, then a held-out test window of 60 days that no model sees during fitting. The champion is additionally subjected to rolling-origin cross-validation over five expanding windows, so that a favourable test period cannot masquerade as model quality.

Evaluation metrics

Accuracy metrics alone are insufficient for a stress application, so the evaluation reports three families.

Metric families and why each is present
FamilyMetricsPurpose
AccuracyMAE, RMSE, MAPE, sMAPE, R², bias, P95 absolute errorAnswers RQ1 and satisfies the proposal's stated metric set.
Peak-restricted accuracyMAE, RMSE, MAPE over the 17:00-21:30 windowAverage accuracy can hide poor performance exactly where the application needs it.
Stress-alarm skillPrecision, recall, F1 against the P95 thresholdTreats the forecast as the alarm it will actually be used as.

Model selection and serving

The ladder exists so the headline number carries meaning: a 3.37% MAPE is informative only against the 7.66% that a seasonal-naive rule achieves on the same window. Gradient boosting was selected as the primary model (AD-02) because the target responds to sharp, threshold-like interactions and because TreeSHAP provides exact attribution at negligible cost.

One serving constraint is deliberate and visible in the code: the model actually deployed is always a tabular estimator, because the serving contract is a design matrix. If a sequence model scores better, the trainer logs that fact explicitly and still serves the tabular champion, rather than silently persisting an artefact the API cannot call.

Explainability

Two SHAP views are produced. The global view ranks drivers over a sample of the test window. The stress-conditional view repeats the analysis restricted to observations above the stress threshold - which is the view a network planner needs, because it answers "what drives the half-hours I care about" rather than "what drives demand on average". A kernel explainer covers non-tree models.

Model lifecycle and release control

Retraining is scheduled; release is gated. The promotion gate applies absolute floors that a model must meet regardless of the incumbent, and relative comparisons against the currently deployed model. Two design choices in the gate are worth stating explicitly.

  • Stress recall is gated harder than precision. A missed stress period is a missed reinforcement signal; a false alarm costs a glance at a dashboard. The asymmetry in the thresholds encodes that asymmetry in consequence.
  • A missing metric is a failure, not a pass. The most dangerous gate is one that approves a model because a metric was absent.

Gate metrics are written onto the registered model as tags, so the next release finds its incumbent without a separate metrics store to keep synchronised.

Security, Governance and Compliance

Data governance

Governance controls
ObligationControl implemented
UK Data Service End User LicenceRaw smart-meter data is never committed to source control (data/raw/ is version-control ignored) and is never transmitted to a public service by this code. Ingestion is designed to run where the data already resides.
No personal data processingThe source extract is anonymised at issue; DRG aggregates further, to groups of roughly 120 households, before any analysis. No output is attributable to a household.
RedistributionThe repository is runnable without the licensed data through a calibrated synthetic generator that contains no real household record, which is what makes the work shareable and reviewable.
Data residencyAll Azure resources are provisioned in a single UK region by default.
RetentionBlob soft-delete is enabled for seven days; log retention defaults to thirty days.

Identity and secrets

  • A single user-assigned managed identity carries every workload permission: registry pull, storage data access and Key Vault secret retrieval. No service-principal credential is stored in an application setting or in the repository.
  • CI/CD authenticates to Azure with OIDC federated credentials; the repository holds only a client, tenant and subscription identifier, none of which is a secret capable of authenticating on its own.
  • The one API key the system may use (OpenWeatherMap) is held in Key Vault and referenced by the container app, never copied into configuration. When no key is supplied the Key Vault reference is not created at all, so the deployment does not carry a dangling secret reference.

NFR-03Latency (interactive)Scenario evaluation returns within a few seconds; forecast endpoints respond promptly.Vectorised simulation over a bounded window; artifacts cached behind an in-process cache. Cold start is accepted as the cost of scale-to-zero and is removable by setting minimum replicas to one.
NFR-04AccuracyThe primary model materially outperforms a seasonal-naive benchmark.Observed: MAPE 3.37% versus 7.66%; RMSE 0.95 versus 2.08; stress-alarm F1 0.90 versus 0.85.
NFR-05ReproducibilityIdentical inputs produce identical outputs.Every stochastic component is explicitly seeded, including a process-stable per-site seed derived by CRC32 rather than by the salted built-in hash. Asserted by test.
NFR-06ReliabilityNo external dependency can stop a run.Retry with exponential backoff, disk caching, and documented degradation for every external call; offline execution is a supported and tested mode.
NFR-07ObservabilityDeployed components are diagnosable without access to the host.Structured logging that attaches an Application Insights handler automatically when the connection string is present; container logs shipped to Log Analytics.
NFR-08TestabilityCore analytics are verifiable offline and quickly.Domain layer free of I/O and framework dependencies. Observed: 103 automated tests in about 36 seconds, fully offline.
NFR-09MaintainabilityConsistent, statically checked code.Enforced lint and format in continuous integration; typed configuration; a single documented feature builder.
NFR-10PortabilityRuns on Windows, Linux and in a container without code change.Path abstraction, no shell dependencies in the library, three container images, and a documented fallback when platform-native binaries for the deep model are unavailable.
NFR-11AccessibilityVisual outputs remain readable in greyscale and with colour-vision deficiency.A validated categorical palette with checked separation, status conveyed by icon and label as well as colour, single y-axes, and a data table beside every chart.
NFR-12CostCloud running cost remains modest for a research deployment.Scale-to-zero API, serverless job scheduling, an ML cluster that idles at zero nodes; estimated USD 60-110 per month at development tier.

Risks, Limitations and Future Work

Architectural risks

Risk register (architectural)
RefRiskImpactMitigation
RA-01Statistical stress is mistaken for an engineering assessment of asset capabilityHighStated in the aim, on the dashboard footer, in this document and in the repository README. The system reports exceedance of a demand distribution, never of a rating.
RA-02Scenario parameters drive headline numbers and could be set to flatter a conclusionHighParameters are configuration, not code; defaults are justified against published planning figures; every scenario reports ADMD and energy per vehicle per day so a reviewer can audit them.
RA-03Public API terms change or a service is withdrawnMediumClients are isolated behind an interface with documented fallbacks; no pipeline stage fails on an unavailable API.
RA-04Concept drift: historical thresholds become unrepresentativeMediumScheduled retraining, gated on stress recall against the incumbent, which surfaces degradation rather than absorbing it.
RA-05Hash-derived neighbourhoods cannot be mapped to physical assetsMediumDocumented as assumption AS-01; the grouping function is a single injection point should feeder identifiers become available.
RA-06Platform-native ML binaries unavailable on an analyst workstationLowImport guarded broadly; a scikit-learn sequence network substitutes automatically so the neural arm of the study remains executable.

Stated limitations

  1. No power-flow modelling. Stress is statistical. Reinforcement decisions require asset ratings and topology that the dataset does not contain.
  2. Carbon intensity before 2018 is a projection, not a measurement. It is tagged as such and contributes under one per cent of model attribution.
  3. Neighbourhood groups are hash-derived, not geographic feeders.
  4. Only uncontrolled charging is modelled. Smart tariffs and managed charging would flatten the reported peaks substantially; the reported figures are therefore an upper bound on unmanaged electrification, which is the appropriate planning case but not a forecast of what will occur.
  5. The reference results in this document were produced on the calibrated fallback dataset. The pipeline, thresholds and simulation are unchanged when the licensed extract is supplied, but absolute figures will differ.
